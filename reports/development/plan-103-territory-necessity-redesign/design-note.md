# Design Note — Plan 103: Territory-Necessity Redesign (`my-side-their-side`)

Status: **gate not cleared — stopped for owner decision (Stop Condition #1)**. No source, test, fixture, or level mutation was made. This note is the required pre-mutation artifact; see `progress.md` in this folder for the packet-process summary.

## 1. What this note establishes

The packet's decided direction was: change Level 20's win condition from "reach a cell" to a flag-carry round trip (`team_scores_point`, matching Level 3's existing vocabulary), so that a reactive threat on the return corridor forces `if_on_my_side`/`if_on_my_side_else` to be the natural, necessary expression of a winning program.

Before touching any board layout or archetype placement, I checked whether that shape is even *expressible* by the level's own toolbox and this engine's execution model. It is not, for a reason that has nothing to do with board geometry or threat placement — it is a hard structural property of the language. I built a throwaway simulation harness (`local/investigations/plan-103/`, gitignored, not part of this deliverable) that clones the real level definition, patches it with a candidate design, and drives it through the real turn engine (`processTurnActions`), and used it to confirm this exhaustively rather than by hand-argument alone.

## 2. Engine fact: there is no program counter across turns

`getFirstRunnableAction` → `resolveFirstRunnableAction` (`src/ai/blockly/workspace.js:711-743`) is called fresh on **every** turn. It walks the "on each turn" block chain from the top and returns the **first** block that resolves to an action. If that first block is a plain movement block (not a conditional), it is returned immediately — the engine never looks further down the stack. This matches the turn-engine doc's own note ("the engine only reads the first executed action from the program; subsequent action blocks in the same turn are skipped") but the consequence is stronger than that note suggests: it applies **every turn**, not just within one turn. A stack of `move_up_screen, move_up_screen, move_forward, move_forward, move_forward` under `on_each_turn` with no conditional between the blocks does not execute as a 5-turn scripted sequence — it executes `move_up_screen` forever, because that first block is the one `resolveFirstRunnableAction` finds every single time.

Verified empirically against the **current, shipped** Level 20 (`try2-baseline-semantics.mjs`): a stack of `move_up_screen ×4, move_forward ×5` (structurally the same shape as the degenerate example cited in this packet's own summary — "`move_forward ×2, move_up_screen ×4, move_forward ×3`") does not reach `(6,2)`. It climbs 4 rows to `(1,2)`, then repeats `move_up_screen` forever against the frozen human runner occupying `(1,1)`, and fails on `turn_limit_exceeded` at the original level's `maxTurns: 12`.

**Consequence for this packet's premise:** the packet's cited justification for why Level 20 needs redesigning — "a student writes `move_forward ×2, move_up_screen ×4, move_forward ×3` and reaches the win cell" — is not literally reproducible in this engine. A plain stack of differing movement blocks with no conditional is dead code beyond the first block. This doesn't mean Plan 93's Guard attempt was fine (see §5), but the specific illustrative mechanism given for *why* it fails is not how the engine behaves.

## 3. Structural proof: a flag-carry round trip cannot be solved with `on_my_side` alone

The only conditional Level 20's toolbox exposes is `if_on_my_side` / `if_on_my_side_else` (`toolboxBlockTypes: [IF_ON_MY_SIDE, IF_ON_MY_SIDE_ELSE, ...EXTENDED_MOVEMENT_BLOCKS]`, and `EXTENDED_MOVEMENT_BLOCKS` is only the four cardinal moves + stay-still — no `move_toward`, no `if_have_enemy_flag`). Given §2, every program buildable from this toolbox reduces to one of two shapes:

- A constant action, forever (no conditional as the first block).
- `if_on_my_side_else { DO: <action>, ELSE: <action> }` — a 2-branch reactive program, re-evaluated every turn purely off current position. (A no-`else` `if_on_my_side` with a following block is behaviorally identical to putting that block in the `ELSE` slot, since `resolveFirstRunnableAction` falls through to the next top-level block when the condition is false and there's no matching branch — confirmed by reading the fallthrough path at `src/ai/blockly/workspace.js:731-739`.)

That gives exactly **25 distinct programs** (5 possible actions × 5 possible actions, the 5 "constant action" cases being the diagonal where `DO == ELSE`). I ran all 25 against a `team_scores_point` win condition on the **open, unmodified board with no threat at all** and a generous 60-turn budget (`try3-exhaustive-no-threat.mjs`), to test pure structural feasibility before any board/threat design:

**Result: 0 of 25 combinations pass.** All 25 fail on `turn_limit_exceeded` at turn 61. (Representative case: `DO=move_forward, ELSE=move_backward` oscillates between `x=5` and `x=6` forever and never reaches the flag.)

**Why this is a hard limit, not a tuning problem:** `on_my_side` is true at the start (spawn is on the home side) and becomes true **again** after the ally returns home with the flag — it flips twice over a round trip, not once. `DO` is a single fixed action and must fire both times. The first occurrence needs `dx=+1` (advance toward the boundary); the second occurrence needs the ally to keep moving `dx=-1` for several more cells to reach an actual `TEAM1_BASE` tile (columns 0–1 only, on `simpleAisle` — confirmed in `src/core/scoring.js:29-33`, `checkForScoring` requires `currentCellType === runnerBaseCellType`, a literal map-tile check, not a configurable "flag home" position, so this can't be designed around by moving the flag-home coordinate closer to the boundary). No single fixed action can be `dx=+1` one time and `dx=-1` the other. This holds regardless of barriers, regardless of any threat archetype or placement, regardless of turn limit — it is a property of the toolbox plus the engine's stateless per-turn evaluation, not of the board.

## 4. Sanity check: composing `if_have_enemy_flag` doesn't rescue this — it makes `on_my_side` incidental

One way out would be to add `if_have_enemy_flag` / `if_have_enemy_flag_else` (Level 3's toolbox) alongside `on_my_side`, nested. I checked whether that's even worth designing around: `if_have_enemy_flag` is **monotonic** across a round trip (false → true once, at pickup, and stays true through the return) — unlike `on_my_side`, it never needs to mean two different things. Isolated test (`try4-haveflag-sanity.mjs`, ally start row aligned with the flag's row to remove the unrelated axis-combining requirement): `if_have_enemy_flag_else { DO: move_backward, ELSE: move_forward }` alone — **no territory sensor at all** — passes in 20 turns.

This means if `if_have_enemy_flag` were added to the toolbox, the natural, laziest winning program would use *only* `if_have_enemy_flag`, and `on_my_side` would be exactly what the packet says it must not be: **incidental**, not the natural expression of the winning program (packet §"Decided Direction," design-freedom bullet 4). Composing the two sensors could still be made to work pedagogically (nest `on_my_side` inside each `have_flag` branch, with a threat whose evasion genuinely differs by side), but that is a materially bigger change than this packet scoped — it turns Level 20 into a two-concept level combining Level 3 and Level 19/20 material, and needs explicit curriculum sign-off, not just a board tweak.

## 5. Reassessing Plan 93's original finding

Given §2, the *current, shipped* one-way Level 20 (`runner_reaches_cell` at `(6,2)`, spawn `(1,6)`) already cannot be beaten by a bare fixed-action program, for the same structural reason: reaching a cell that differs from spawn in both `x` and `y` requires combining two different movement axes, and the only way to combine two different actions in this toolbox is the `on_my_side` conditional. In that narrow sense, `on_my_side` is already structurally load-bearing for the shipped level, contrary to this packet's summary of Plan 93's finding ("no position-based sensor is ever strictly necessary... any winning trajectory can be reproduced by a fixed action sequence").

That doesn't mean Plan 93's Guard attempt was sound, though. The actual reference program is `if_on_my_side_else { DO: move_forward, ELSE: move_up_screen }`, which produces one specific L-shaped path: straight across row 6 to `(6,6)`, then straight up column 6 to `(6,2)`. Plan 93's reverted attempt posted a Guard at `(8,6)` with `guardRadius: 2` — off the reference path's column entirely (the path only ever touches column 6, never columns 7–10). The real, narrower flaw was very likely that the Guard's post/radius never actually intersected the one path the reference program travels, not that "any" hardcoded path exists to route around it. That's a fixable, ordinary placement problem for a one-way level, not evidence that position sensors are categorically incompatible with reach-a-cell levels here.

## 6. Conclusion and required owner decision (Stop Condition #1)

The packet's accepted direction — flag-carry round trip, using only the existing `on_my_side` toolbox — **cannot be built**. This isn't a "still hardcodable, try a different board" outcome (which the packet already anticipated and told me to stop on); it's stronger: no board or threat design can make it work, because the toolbox itself cannot express the round trip at all. This is exactly Stop Condition #1 as written: *"No proposed objective makes `on_my_side` load-bearing without changing the taught concept — surface for an owner decision on whether Level 20 should keep territory at all, or become an honest non-gated teaching level."*

Options, for owner decision:

- **(a) Revisit the one-way shape, but fix the actual flaw.** Keep `runner_reaches_cell`, keep the toolbox as-is. Per §5, `on_my_side` is already structurally necessary for combining axes here — the missing piece is a threat placement that actually intersects the one reachable winning path (verified by simulation, not eyeballed). This directly contradicts this packet's non-goal ("do not re-attempt a board-only fix on the existing reach-a-cell objective... out of scope"), which was written on the premise that any hardcoded path is possible — a premise §2–§3 show doesn't hold in this engine. I'm not doing this without sign-off since the packet explicitly ruled it out, but the evidence for why it was ruled out doesn't hold up.
- **(b) Add `if_have_enemy_flag` to the toolbox and design a two-sensor level.** Bigger curriculum change (Level 20 becomes a composition of Level 3 + territory material); needs a threat whose evasion genuinely differs by side so `on_my_side` isn't incidental per §4. Out of this packet's stated scope as written.
- **(c) Drop necessity-gating for Level 20.** Keep it an honest, ungated teaching level (accurate `boardDynamicsTier`, no `mechanicNecessity: "dynamic"` claim). Lowest risk, smallest change, matches the packet's own fallback language.
- **(d) Redesign the map's base geometry** so the team's base sits adjacent to the territory boundary (eliminating the long "walk home" leg that forces the second, incompatible `DO` firing). Not recommended — `simpleAisle`'s 2-column base is shared by many levels; a level-specific map would be a materially bigger architectural change than "board layout / barriers," which is what the packet's design freedoms describe.

My recommendation is **(a)**, since it's the smallest change, doesn't touch the toolbox or taught concept, and reuses the packet's own "reuse existing win-condition vocabulary" instinct — but it requires the owner to formally lift the non-goal that currently forbids it, since that non-goal's premise is what §2–§5 challenge. I have not implemented anything pending that decision.
