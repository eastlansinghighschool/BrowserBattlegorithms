## Repair A — Frozen + index badge collision (Plan 58, Req 3 violation)

`drawRunnerLabelBadge` in `src/render/effects.js` currently moves the index badge to the **upper-left** of the cell (`pixelY + 3`) when the runner is frozen and not human-controlled:

```js
if (runner.isFrozen) {
  if (runner.isHumanControlled) {
    badgeY = runner.pixelY + (CELL_SIZE - badgeHeight) / 2; // midline
  } else {
    badgeY = runner.pixelY + 3; // upper-left  ← THIS COLLIDES WITH FROZEN BADGE
  }
}
```

The frozen countdown badge from `drawFrozenCountdownBadge` already renders in the upper-left at the same coordinates. So a frozen non-human runner with `showRunnerIndexBadges` on will have the two badges drawn on top of each other. The packet's Decision 5 and Req 3 both say the index badge belongs in the **lower-left** specifically to avoid this collision.

**Fix:** Remove the special-case repositioning for frozen non-human runners. The default lower-left position is the correct position regardless of frozen state. Keep the midline displacement for human-controlled runners only (this avoids the upper-left "P1"/"P2" label in PvP). Result:

```js
const badgeHeight = 14;
const badgeX = runner.pixelX + 3;
let badgeY = runner.pixelY + CELL_SIZE - badgeHeight - 3; // default lower-left

if (runner.isHumanControlled) {
  // Avoid overlap with the upper-left "P1"/"P2" label in PvP mode.
  // (The label is drawn at pixelX+2, pixelY+2 by drawHumanPlayerLabels in PvP only,
  // but the displacement is cheap to apply unconditionally for human runners.)
  badgeY = runner.pixelY + (CELL_SIZE - badgeHeight) / 2;
}
```

**Also fix the test:** `tests/unit/runner-label-badge.test.js` test "calculates correct position for default, frozen, and frozen-human states" currently encodes the bug. Replace Case 2 with: "frozen non-human still uses default lower-left position" asserting `badgeY === pixelY + CELL_SIZE - badgeHeight - 3`. Add a new Case for "human non-frozen uses midline position" asserting `badgeY === pixelY + (CELL_SIZE - badgeHeight) / 2`.

Note: the comment Gemini wrote in code referring to a "bottom human 'YOU' label" is wrong. The actual human label is `drawHumanPlayerLabels` in `src/render/drawEntities.js:38-57` which writes "P1"/"P2" at `pixelX + 2, pixelY + 2` (upper-left), and only in PvP mode. Update the comment to match reality.

## Repair B — Duplicate "0" badge on teams with both a human and a code-controlled ally (Plan 58, Req 2 + Decision 7 violation)

In `src/core/setup.js`, the `allyIndex` field is assigned only to code-controlled non-human, non-NPC runners (starting at 0). Human-controlled runners and NPCs have `allyIndex = null`.

Gemini's fallback in `drawRunnerLabelBadge` uses array-position-within-team for runners that lack `allyIndex`:

```js
const sameTeamRunners = state.allRunners.filter((r) => r.team === runner.team);
const listIndex = sameTeamRunners.indexOf(runner);
```

On a team with a human at array position 0 and one code-controlled ally at array position 1:
- Human runner: `allyIndex = null` → fallback → list index `0` → badge shows **"0"**
- Code-controlled ally: `allyIndex = 0` → badge shows **"0"**

Both runners on the same team display "0", which defeats the entire point of the index badge (disambiguation). Decision 7 of the packet explicitly required that "the numeric index disambiguates runners on the same side."

**Fix:** Make the fallback skip the runners that already have an `allyIndex` set, so the namespaces do not collide. Compute the fallback index over the subset of same-team runners that *also* lack `allyIndex`:

```js
const sameTeamFallbackRunners = state.allRunners.filter(
  (r) => r.team === runner.team
    && (typeof r.allyIndex !== "number" || !Number.isFinite(r.allyIndex))
);
const listIndex = sameTeamFallbackRunners.indexOf(runner);
```

This produces a separate numbering for code-controlled allies (0, 1, 2…) and for non-allyIndexed runners (humans + NPCs) on the same team (also 0, 1, 2…). On a team with 1 human + 2 code allies, the human shows "0" (its index among non-allyIndexed) while the allies show "0" and "1" (their `allyIndex` values). Still a collision between the human's "0" and ally #0's "0".

A cleaner alternative: give every non-allyIndexed runner a numbering offset by `state.allRunners.filter(r => r.team === runner.team && typeof r.allyIndex === "number").length`. So the human's badge becomes "2" (after allies 0 and 1) on a 1-human-2-allies team. Pick this approach if you want a single namespace per team.

**Owner decision needed (escalate to integration owner before implementing the fix):** which numbering scheme do we want on mixed-control teams?

1. **Separate namespaces** (humans and NPCs use their own 0/1 series, code allies use the `allyIndex` series): simpler implementation, but produces same-number badges on the same team. Defeats disambiguation.
2. **Single namespace** (humans and NPCs get numbers that follow the allyIndex range): truly disambiguating, but the human's badge number depends on how many code allies exist on the team, which feels arbitrary.
3. **Side-prefix labeling** (e.g., humans get "H", NPCs get "N", code allies get "0/1/2"): packet Decision 3 said numeric only, no letter prefix. Would require a packet decision change.

My lean: option 2 (single namespace) — preserves Decision 3 and actually disambiguates. Document the derivation in the progress report per Decision 6.

Note that the current unit test for the index resolution uses a state with one ally + one enemy and does not exercise this bug. Add a test covering: team with human + code ally → badges must differ.

## Repair C — Smoke spec doesn't verify badge rendering (Plan 58, Validation Checklist violation)

`tests/browser/runner-index-badge.spec.js` only toggles the checkbox and reads `app.state` to verify state changes. The Plan 58 validation checklist explicitly required:

- "With the gear toggle on, every ally on Level 30 shows a numeric badge with the ally team color tint."
- "With the gear toggle on, every enemy on Level 30 shows a numeric badge with the enemy team color tint."
- "A frozen ally shows BOTH the frozen countdown badge (upper-left) AND the index badge (lower-left) without visual overlap."

None of these are exercised. The smoke spec is a settings test, not a render verification test, which is exactly why Repair A's collision and Repair B's duplicate-number bug both shipped past validation.

**Fix:** Add a second test in `runner-index-badge.spec.js` (or a sibling spec) that:

1. Loads Level 30 (`?devGuidedLevel=...` query or equivalent based on the existing harness — see `tests/browser/dev-guided-level-link.spec.js` for the pattern).
2. Enables `showRunnerIndexBadges` via the gear.
3. Takes a canvas pixel sample at the expected lower-left badge position of each runner and asserts the pixel is the team's tinted color (not transparent / not the background color). Use `page.evaluate` to read pixels via `canvas.getContext('2d').getImageData(...)` — but note p5 uses webgl by default, so confirm rendering mode and fall back to a different verification if needed.
4. As a backup if canvas pixel reading is impractical: assert via `page.evaluate` that `drawRunnerLabelBadge` was called for each runner, by instrumenting the function with a call counter exposed via `window.__BBA_TEST_HOOKS__`. Less direct but verifiable.

If canvas pixel verification is too fragile, the call-counter approach is acceptable — but document the choice in the progress report.

This is the highest-leverage repair because it would have caught both Repair A and Repair B before they shipped.

## Repair D — Two parallel `document.addEventListener("keydown")` listeners (Plan 57, Req 7 violation)

`src/ui/controls.js` adds **two** `document.addEventListener("keydown", ...)` calls — one for the focus trap, one for ESC closing the settings modal. Plan 57 implementation requirements implicitly inherit the Plan 56 rule (and the broader project rule from `docs/subsystems/p5-surface-map.md`): keyboard input belongs in `handleKeyInput`, not in parallel document-level listeners.

The ESC consumer is also overly aggressive: it calls `event.preventDefault()` and `event.stopPropagation()` unconditionally when the settings modal is open. If the cell inspector's ESC handler (which also lives in `handleKeyInput`) needs to fire while the settings modal is incidentally open, it won't.

**Fix:**

- Move the ESC-closes-settings-modal logic into `handleKeyInput`, right next to the existing `unpinCellInspector` ESC branch. Order it after the inspector check (so a pinned tooltip unpins first; second ESC closes the modal).
- The focus trap genuinely does need a Tab listener that the in-game `handleKeyInput` does not see (handleKeyInput only fires for keys that p5 forwards via `keyPressed`, and Tab is not one of those in normal gameplay). Acceptable to keep the focus-trap listener as a document-level keydown, but gate it tightly: attach only when the modal opens, detach when it closes. Do not leave it permanently attached.

If unsure, escalate: the spirit of the rule is "no parallel input pipelines," but a Tab-only focus trap that's only active while a modal is open is borderline acceptable. The ESC duplication is not.
